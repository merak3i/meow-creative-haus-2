# my laptop has a skill issue

the useful kind / what i keep asking AI to do, and where the small instructions earn their place

by vismay hegde · meow creative haus · 15 september 2026

i asked for a tier list of the skills i use on this laptop

i expected a slightly embarrassing inventory. lots of installed things, a few familiar ones, perhaps an instruction file i had forgotten about explaining why every answer sounded like a manager announcing a restructure

the surviving records pointed to something more ordinary

i keep asking for the writing to sound like me. for the answer to appear somewhere i can use it. for the assistant to open the actual page and check whether the thing works

there is coding in the history too. but plenty of the repeated work happens between having an idea and having something another person can read, approve or use

## a small receipt is still a small receipt

the scan covered 289 Codex log files, 1,001 Claude Code files, 583 Cursor transcript files and 50 Antigravity transcripts, plus the Hermes conversation database

Cursor's exports collapsed to 499 transcript IDs. the oldest recovered timestamp was 12 may 2026; other apps had shorter or less clearly dated histories

these are different evidence windows, so there is no honest single number for “most used ever”

writing appeared in 127 Cursor transcript IDs. chat delivery in 129. rocky in 280, with a large qualification: it is configured as a default voice. that frequency includes the effect of an instruction, not just deliberate choices i made at the keyboard

the counts are explicit skill-call or file-read requests. they do not prove the read succeeded, the instructions were followed, or the result was good. identifiable scheduled and delegated work was separated where the records allowed it

all four transcript sets were machine-scanned. selected request-and-outcome windows were reviewed more closely. nobody manually read every line and emerged with a scientific measurement of my productivity

the tiers below are my editorial judgment. the examples are anonymous composites of the work patterns, not client case studies or measured savings

## S tier is a lot of editing and checking

writing earns its place when the model preserves what i meant

the core job is simple enough. take a rough note from a software founder, remove the repeated setup, explain the unfamiliar term, keep the slightly uneven voice

the edge case is more consequential. the draft says a small pilot suggests a benefit. the polished version says the product delivers that benefit

that edit changed the claim

i want the skill to keep the sample size and uncertainty, even if the stronger sentence sounds nicer. writing cleanup belongs near this work too. there is little value in removing a fashionable phrase while quietly adding confidence the evidence never had

chat delivery is another S-tier habit. an education team asking for a caption and image should get one final caption block, the right image and its posting order

now add two exports with similar names, one containing old pricing. the handoff needs to identify the current version and separate final copy from commentary. otherwise the person receiving it inherits a small investigation

the concise-answer habit helps here. the goal is to make the state clear enough to act on. an answer can be short and still say what remains unverified

## open the actual page, please

browser verification is S tier because a build result answers only part of the question

suppose the task is to add a public page with a download. the useful check starts at the menu, opens the page, tries it on a phone and downloads the file

then there is the awkward version. the build passes, but the hosted preview asks for a login. or the page opens locally while the public route still returns 404

the correct handoff keeps those states separate. calling the preview a live success would erase the exact fact the user needs

in the eligible Codex records, computer-use appeared in 17 source sessions, control-chrome in 17, and control-in-app-browser in 10. those groups overlap. adding them would produce a tidier number and a worse explanation

documents earn S tier for similar reasons. a recurring invoice should preserve its reference. a report should survive export without a table running into the footer

my current PDF default is three pages unless i ask for more. that creates an editing job: choose the information, build a readable grid and remove repeated explanation

if a caveat or unit disappears to make a table fit, the document got smaller by becoming less useful. restore the important detail and cut something else. then render every page and look at it

this carousel has fifteen slides because i explicitly asked for fifteen. the exception is doing exactly what it says

social content sits alongside these skills. a technical note needs a reading sequence, not just a different aspect ratio. an operations buyer may need an example about a handoff they manage, while a technical reader needs the implementation detail. changing the reader should change the explanation and the proof

## A tier is where context starts to matter

research and source retrieval are useful before the confident sentence

an old announcement might say a service includes a feature. the current support page might describe a narrower version. the job is to explain the date and scope difference, not blend both pages into an answer that neither supports

buyer research has a related failure mode. a hiring post may suggest expansion. it does not prove that an organization intends to buy, or that its internal process is broken

the core GTM task is a grounded brief and a relevant draft. a technical owner and a procurement lead need different details because they have different responsibilities. the edge-case discipline is keeping a business signal from becoming invented inside knowledge

questions are useful when an answer changes the work. “publish the report” may need clarification if the destination could be internal or public

but if the user already named the destination, audience and format, another interview is friction. grilling had 23 Codex read requests concentrated in two source sessions. that is a useful reminder of how easily repeated calls can look like a broad habit

## Hermes has a different working week

the retained Hermes database contained 41 sessions: 34 cron, six desktop and one subagent

its busiest list is largely a record of scheduled work. ops-rhythm had 21 observed requests across 12 scheduled sessions. Apollo tooling had 18 across six. GTM had eight across seven

a recurring brief is useful when it tells someone what changed and what decision is needed

the edge case is a source that stopped updating. the scheduler still runs, and the output may still look complete. the brief needs the last successful source date and an explicit gap, rather than another paragraph assembled from stale material

one reviewed scheduled example encountered unavailable integrations and returned a handoff. execution frequency did not establish integration health

this is why i keep the scheduled slice separate from the things i reach for during desktop work

## the odd tools i want nearby

vision workarounds are an A-tier specialist. if the active model cannot inspect an image normally, available OCR can recover text and basic analysis can measure some structure

the interesting case is a character that matters. a reference number could contain O or 0. mark the uncertainty and get a clearer source before carrying it into a consequential document

two Hermes desktop sessions requested this kind of help. the audit did not measure recovery accuracy

finance-document work has a similar need for restraint. changing the month and description in a reference invoice is a bounded task. guessing a new tax treatment because last month's document had a rate is a different action. ask for the authoritative input, verify affected arithmetic and inspect the export

context recovery and existing-data discovery also stay in the kit. a rough timestamp can help find the right draft. an authorized export may already contain the fields needed for a data task

but two drafts can share a name, and a promising endpoint can be stale. inspect the actual content and freshness. a read request for a discovery skill does not prove that an endpoint was accessed or useful

## what i would actually keep

my S tier is writing, delivery, the concise-answer habit, browser checks, document production and social-format work

A tier covers research, buyer preparation, recurring briefs, image fallback, precise finance edits, context recovery, decision questions, existing-data discovery and release review

review earns its place when it changes the next run. a clipped footer can produce a rendered-page check. an inaccessible public URL should keep a release marked incomplete. adding more checklist boxes does not repair either result

the public skill kit turns these patterns into short, editable instructions. each includes the inputs, expected output and limits. it supplies no browser access, OCR engine, paid integration or permission to send anything

some history remains unavailable. Cursor's large application database was not decoded; its readable exports were used. OpenCode's database could not be opened read-only. there was no readable history at the checked Gemini CLI, Pi and Continue defaults, and one Antigravity record was malformed

missing records do not mean missing usage

for the next task, i would choose one skill, give it the real reference and check the result. if it catches a mistake i keep making, that is a reason to keep it
